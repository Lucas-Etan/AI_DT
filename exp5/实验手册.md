# 实验 05：Transformer 与大语言模型推理基础

* **Transformer**：一种使用注意力机制的神经网络结构；注意力机制会根据当前任务，为输入中不同位置分配不同的关注程度。
* **大语言模型（LLM）**：在大量文本上训练、能够根据输入继续生成文本的模型；本实验使用的 Qwen 属于这一类模型。

> 课程：人工智能开发技术（Python）  
> 学时：4 课时<br>
> 必做主路径：Qwen2.5-0.5B-Instruct 本地 CPU 推理  
> 可选路径：兼容 Chat Completions 的在线接口；无合法配置时安全跳过  
> 设备假设：Windows、Python 3.12、CPU、约 16 GB 内存

* **Chat Completions**：一种按 system、user、assistant 等角色消息组织请求和回答的在线模型接口形式。

## 1. 实验内容与目的

### 先看看它能解决什么问题

大语言模型接收的是文本，但应用真正需要的往往不只是“一段看起来通顺的话”，还可能要求稳定的格式、有限的上下文和可控制的生成方式。下面先看几个具体场景，第一行是本实验实际完成的任务。

* **上下文（context）**：本次生成时模型能够看到的系统消息、历史对话和当前问题；它有长度上限，并不是永久记忆。

| 实际场景 | 输入什么 | 系统做什么 | 最终得到什么 |
|---|---|---|---|
| 本实验：本地问答与学习计划生成 | 一段自然语言问题或学习计划要求 | 用本地 Qwen 小模型逐 token 生成，并把计划解析为受约束的 JSON | 普通文本回答，或通过 Pydantic 校验的结构化学习计划 |
| 个人学习助手 | 学习目标、可用天数和每日时间 | 按固定字段组织模型输出并检查取值范围 | 可以被日历或学习应用继续使用的计划数据 |
| 多轮客服助手 | 当前问题和此前的对话消息 | 在 token 预算内保留最重要的上下文后生成回复 | 与最近对话相关、长度可控制的回答 |
| 自然语言表单填写 | 用户描述的活动、任务或配置需求 | 从生成文本中提取 JSON，并依次检查语法、字段类型和业务规则 | 可由程序读取的结构化记录，或清楚的校验失败信息 |

* **token**：模型处理文本时使用的基本片段，可能是一个字、一个词或词的一部分，不等同于 Python 字符数。
* **Pydantic**：根据预先声明的字段、类型和规则检查 Python 数据的库，本实验用它判断模型生成的 JSON 能否被程序安全接收。
* **结构化输出（structured output）**：按照固定字段和数据类型组织的输出，例如包含主题、难度和时间的 JSON，而不是任意自然语言段落。

本实验不会训练大模型，而是把现有模型变成一个可调用、可控制、可验证的软件组件。同学们将看到 token、解码参数、上下文裁剪和结构化校验如何共同影响最终应用。

* **解码（decoding）**：把模型给出的下一 token 分数转换成具体 token，并重复这一过程形成文本；不同解码参数会改变稳定性和多样性。
* **上下文裁剪（context trimming）**：超过预算时按规则删除较旧消息，同时尽量保留系统要求和当前问题。

### 1.1 实验内容

本实验不训练大模型，而是把“文本如何进入模型、模型如何逐 token 生成、参数如何改变输出、上下文如何裁剪、自然语言如何变成可信结构化数据”拆成可观察的五个阶段。

你收到的是现成实验骨架。可以按下面的顺序推进：

`复制骨架项目 → 建立独立 .venv → 打开指定现有文件 → 定位 FILL 编号 → 理解输入输出 → 填写关键代码 → 运行对应脚本 → 对照预期结果`

### 1.2 实验目的

完成本实验后，你应能：

1. 解释 token、token ID、聊天模板和生成提示后缀各自的作用。
2. 用 Transformers 在 CPU 上加载一个小型 Qwen 指令模型，并只解码新生成 token。
3. 比较贪心、低温采样和高温采样，理解 Temperature、Top-p 与随机种子的关系。
4. 按 token 预算裁剪多轮消息，同时保留系统消息和最新问题。
5. 从可能带额外文本的生成结果中提取 JSON，并用 Pydantic 做字段、范围和业务规则校验。
6. 区分“JSON 语法正确”“字段类型正确”“业务上可接受”三个层次。
7. 在无在线配置时得到诚实的 `SKIP`；有合法配置时复用同一结构化校验逻辑。
8. 记录模型缓存、加载时间、生成时间和进程内存，认识 CPU 推理的质量与资源限制。

* **token ID**：token 在词表中的整数编号；模型实际接收和输出的是这些编号。
* **聊天模板（chat template）**：把 system、user、assistant 等角色消息拼成模型训练时熟悉的特殊格式。
* **贪心解码与采样**：贪心解码每一步都选择分数最高的 token；采样则按概率随机选择，因此输出更有变化。
* **Temperature**：调节概率分布尖锐程度的参数；通常越低越稳定，越高越随机。
* **Top-p**：只在累计概率达到指定比例的高概率候选中采样，用来排除概率很低的 token。

**学习起点与进阶顺序。** 只要熟悉 Python 函数、列表、字典和 JSON，就可以开始本实验。同学们会先观察 token 和聊天模板，再运行本地生成与解码比较，随后处理上下文预算，最后才进入 JSON 提取、Pydantic 校验和可选在线接口。

## 2. 问题拆解与核心机制

### 2.1 推理链路

本实验的本地推理链路为：

`messages → chat template → input_ids → model.generate → output token IDs → 截取新增部分 → decode → 文本`

任何一步混淆都可能造成典型错误：

- 跳过聊天模板：模型看到的角色边界与训练时不同。
- 解码整段输出：回答前重复系统消息和问题。
- 没有限制 `max_new_tokens`：CPU 等待时间不可控。
- 把采样参数用于贪心：比较不公平或产生警告。

### 2.2 token 不是汉字或单词的简单计数

文本进入模型前，需要先由 Tokenizer 转换成编号。

* **Tokenizer（分词器）**：把字符串切成 token 并映射为整数 ID，也能把 ID 还原成文本。一个汉字串可能是一个 token，也可能被拆成多个片段；上下文上限通常按 token 计算，不按 Python 的 `len(text)` 计算。

### 2.3 自回归生成

本实验使用因果语言模型逐步生成回答。

* **因果语言模型（causal language model）**：根据已有 token 预测下一个 token，再把新 token 追加到序列中继续预测。这个逐步向后生成的过程也称为自回归生成。

贪心每步取最高概率；采样从经过 Temperature 和 Top-p 调整的分布中抽取。固定种子可提高对照性，但不同库版本、硬件和并行策略仍可能带来差异。

### 2.4 上下文是有预算的

模型虽声明较大上下文上限，实际应用仍需为输出留空间并控制延迟。骨架使用较小的 160-token 教学预算，成对删除最旧的 user/assistant 历史，保留系统消息和最新用户问题。

### 2.5 生成文本不等于可信对象

结构化处理分三关：

1. 语法关：找到完整花括号对象，并由 `json.loads` 验证。
2. 模式关：Pydantic 检查字段存在、类型、长度、数值范围和额外字段。
3. 业务关：例如难度达到 4 时，学习时间不得少于 30 分钟。

模型输出即使看起来合理，也必须经过程序校验。校验失败应记录为失败，而不是偷偷改成期望答案。

### 2.6 本地与在线共用边界

本地模型和在线接口都返回文本，随后共用 `extract_json_object` 和 `StudyPlan`。这样可把“模型提供者差异”与“应用数据契约”分开。密钥只放当前 PowerShell 会话的环境变量，不写入源码、截图或提交物。

### 5.2 FILL-01：固定随机性与 CPU 线程

定位并打开现有文件：

```powershell
Select-String -Path .\runtime_utils.py -Pattern "TODO\(FILL-01\)"
notepad .\runtime_utils.py
```

预期结果：定位到 `prepare_cpu` 函数中的 `FILL-01`。

CPU 推理要尽量可复核，也要避免小模型把普通电脑的全部线程占满。下面同时固定 Python/Torch 随机源，并把计算线程限制到课程配置值；它为后续所有本地生成提供统一运行条件。

```python
random.seed(SEED)
torch.manual_seed(SEED)
torch.set_num_threads(CPU_THREADS)
torch.set_num_interop_threads(1)
```

逐行理解：

- Python 与 Torch 各自有随机状态，两者都固定。
- 计算线程限制为 `settings.py` 中最多 4 个，避免 16 GB 普通电脑上抢占过强。
- 互操作线程用于算子调度，设为 1 减少小模型推理抖动。
- 同一进程内应在首次并行计算前调用，不能反复修改互操作线程。

### 5.3 FILL-02：加载本地 tokenizer 与模型

定位并打开：

```powershell
Select-String -Path .\local_llm.py -Pattern "TODO\(FILL-02\)"
notepad .\local_llm.py
```

**理论说明：** 本实验要在没有 GPU 的电脑上直接运行 Qwen2.5-0.5B-Instruct，因此需要显式加载相互匹配的 tokenizer 和模型、固定本地缓存目录并强制使用 CPU。下面返回的两个对象会被 token 观察、文本生成和结构化输出三个阶段共同复用。

```python
tokenizer = AutoTokenizer.from_pretrained(MODEL_ID, cache_dir=CACHE_DIR)
model = AutoModelForCausalLM.from_pretrained(
    MODEL_ID,
    cache_dir=CACHE_DIR,
    dtype=torch.float32,
).to("cpu")
model.eval()
if tokenizer.pad_token_id is None:
    tokenizer.pad_token = tokenizer.eos_token
return tokenizer, model
```

关键解释：

### 7.1 FILL-03：只解码模型新增 token

**理论说明：** `generate` 返回的是“完整提示 + 新生成内容”的 token 序列，如果直接整体解码，回答会把 system 和 user 原文重复出来。下面先记录提示长度，再只截取模型新增的 token，并同时返回提示与新增长度供性能分析。

```python
inputs = tokenizer.apply_chat_template(
    messages, tokenize=True, add_generation_prompt=True,
    return_dict=True, return_tensors="pt",
)
prompt_length = inputs["input_ids"].shape[-1]
with torch.inference_mode():
    output_ids = model.generate(
        **inputs, max_new_tokens=max_new_tokens,
        pad_token_id=tokenizer.pad_token_id, **sampling,
    )
new_ids = output_ids[0, prompt_length:]
text = tokenizer.decode(new_ids, skip_special_tokens=True).strip()
return text, prompt_length, len(new_ids)
```

关键解释：

- `return_dict=True` 让结果能直接展开给 `model.generate`。
- `prompt_length` 是输入序列长度，不是字符数。
- `torch.inference_mode()` 关闭梯度记录，降低 CPU 推理额外开销。
- `output_ids` 包含提示和回答，所以从 `prompt_length` 开始切片。
- 只对 `new_ids` 解码，避免回答重复问题。
- 同时返回 token 数，便于比较输出长度和时间。

### 8.2 FILL-09：保留系统消息与最新问题

定位：

```powershell
Select-String -Path .\03_context_window.py -Pattern "TODO\(FILL-09\)"
```

**理论说明：** 当多轮对话超过预算时，我们希望优先删除最旧历史，同时始终保留系统约束和最新问题。下面按一组 user/assistant 两条消息逐步裁剪，并在连这两端都放不下时明确失败，避免静默截断语义。

```python
system = messages[:1] if messages[0]["role"] == "system" else []
newest = messages[-1:]
history = messages[len(system):-1]
while history:
    candidate = system + history + newest
    if token_count(tokenizer, candidate) <= max_tokens:
        return candidate
    history = history[2:]
candidate = system + newest
if token_count(tokenizer, candidate) > max_tokens:
    raise ValueError("system 加最新问题仍超出预算，请缩短文本")
return candidate
```

关键解释：

- 系统消息单独保存，不能随最旧历史一起删除。
- 最新用户问题单独保存，否则模型可能回答已经被删掉的旧问题。
- 每次删除两条，保持 user/assistant 对成组。
- 历史全部移除仍超预算时显式失败，不进行静默字符截断。

### 9.1 FILL-10：提取首个完整 JSON 对象

**理论说明：** 模型可能在 JSON 前后附加解释、换行或 Markdown 围栏，应用不能把整段文本直接交给业务逻辑。下面从第一个左花括号开始追踪嵌套深度，同时识别字符串和转义字符，提取第一个完整 JSON 对象并先做语法解析。

```powershell

```

在定位到的 FILL-10 中放入下面的状态扫描逻辑：

```python
start = text.find("{")
if start < 0:
    raise ValueError("输出中没有 JSON 对象起始符 {")
depth = 0; in_string = False; escaped = False
for index, char in enumerate(text[start:], start=start):
    if char == '"' and not escaped:
        in_string = not in_string
    if not in_string:
        depth += char == "{"; depth -= char == "}"
        if depth == 0:
            candidate = text[start:index + 1]
            json.loads(candidate); return candidate
    escaped = char == "\\" and not escaped
    if char != "\\": escaped = False
raise ValueError("JSON 对象没有闭合")
```

关键解释：

- 从第一个左花括号开始，花括号深度回到 0 时得到候选对象。
- 字符串内部的花括号不参与深度计算。
- `escaped` 防止转义双引号错误切换字符串状态。
- 返回前调用 `json.loads`，语法错误不会进入 Pydantic。
- 这里只提取第一个对象；模型输出多个对象时，其余内容不被信任。

**QA：** 若本地生成显示 `validation=FAIL`，先保留原始输出，再根据错误区分“没有完整 JSON”“JSON 语法错误”“字段约束失败”或“跨字段规则失败”；程序无误时可以重新生成，但不能把失败改成 PASS。若四类固定反例出现 `UNEXPECTED_PASS`，按上面的 FILL 对应关系修复校验代码；若 JSON 中字符串含花括号时被提前截断，检查 `in_string` 和 `escaped` 状态更新。

### 9.8 带学号的最终验收截图

**理论说明：** 四类反例用来确认类型、范围、重复值和跨字段规则确实会被拦截；校验完成后再显示身份信息，可以把四个拒绝结果与本次验收时间保留在同一窗口。

### 11.2 质量限制

1. 0.5B 模型适合 CPU 教学，但生成内容可能流畅却概念不严谨，并出现模型幻觉。
2. 固定种子不保证不同 Transformers 或 Torch 版本逐 token 完全一致。
3. `max_new_tokens=32` 适合短句，不适合长解释；结构化阶段单独使用 96。
4. 进程 RSS 包含解释器、库和临时张量，不等于模型权重大小。
5. 上下文裁剪采用简单“删除最旧对话”，没有摘要、检索或重要性评分。
6. Pydantic 只能验证定义过的规则，不能自动判断知识事实是否正确。
7. 在线服务的隐私、日志留存、配额和内容政策由提供者决定；请勿上传敏感课程、个人或业务数据。
8. 不把 3B 级本地模型设为必做，因为在 CPU 和 4 课时约束下加载与生成可能显著变慢。

* **模型幻觉（hallucination）**：模型生成了看似合理、但没有输入依据或与事实不符的内容；语言通顺并不能证明答案正确。
* **RSS（常驻内存集）**：当前进程实际驻留在物理内存中的数据量，可用来观察程序运行时的内存占用。

## 13. 常见问题与排查（QA）

### Q1：`py -3.12` 找不到解释器

执行 `py -0p` 查看已安装解释器。安装 Python 3.12 后重新建立本实验 `.venv`，不要复用其他实验环境。

### Q2：激活脚本被执行策略阻止

执行 `Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass`，只修改当前 PowerShell 进程，再重新激活。

### Q3：安装到了带 CUDA 依赖的 Torch

卸载当前 `.venv` 中的 torch 后，使用第 4.3 节给出的 CPU wheel 索引安装。`00_env_check.py` 的设备选择仍应为 CPU。

### Q4：导入 torch 时出现 DLL 错误

确认 Python 与 wheel 都是 64 位，安装系统的 Microsoft Visual C++ 运行库，并重新安装 CPU wheel。不要从非官方镜像复制单个 DLL 到项目。

### Q5：`pip check` 报依赖冲突

确认 `Get-Command python` 指向当前 `.venv\Scripts\python.exe`。若环境混入其他课程包，复制一份新的骨架项目并重新建立独立环境。

### Q6：模型下载很慢或中断

缓存保存在当前项目 `hf_cache`。重试时已完成文件通常会复用。不要同时打开多个模型下载脚本，以免重复占用带宽和磁盘。

### Q7：校园代理无法访问模型仓库

先按学校规范配置网络代理；仍无法解决时，请记录完整错误并通过课程支持渠道获取合规缓存。请勿从来源不明的网盘下载模型权重。

### Q8：缓存接近 1 GB，是否异常

本实验缓存约为 953.3 MiB，其中包含约 942.3 MiB 权重以及 tokenizer、配置等文件，属于预期范围。

### Q9：加载时内存超过权重大小

模型对象、Python 运行时、库、生成缓存和临时张量都会占内存。进程峰值的自查参考约为 3.1 GB；关闭其他大型应用可留出余量。

### Q10：CPU 推理数分钟无输出

先看任务管理器是否仍有 CPU 活动，并把 `max_new_tokens` 保持为手册值。不要把 3B 或更大模型替换为必做模型。

### Q11：`set_num_interop_threads` 报不能再次设置

`prepare_cpu` 必须在本进程首次并行工作前调用，且不应在同一进程反复执行。按编号脚本分别启动新 Python 进程即可。

### Q12：`00_model_check.py` 抛 `NotImplementedError`

先完成 `FILL-01` 和 `FILL-02`，替换 TODO 与异常语句并保存。错误文本会提示对应编号。

### Q13：token 数与手册不完全相同

先核对模型 ID 和 Transformers 版本。tokenizer 文件更新可能改变 ID 或片段；记录自己的版本和结果，不要硬改输出。

### Q14：生成结果重复了系统消息或问题

检查 `FILL-03` 是否从 `prompt_length` 开始切片，只解码 `new_ids`。

### Q15：贪心运行出现 Temperature 无效警告

确认 `FILL-06` 的 `greedy` 只有 `do_sample=False`，不要附带 Temperature 或 Top-p。

### Q16：三种采样结果完全相同

短提示和高概率分布可能产生相同结果。仍需确认 `do_sample=True`、温度和 Top-p 确实传入，并保留真实观察。

### Q17：上下文裁剪后超过 160 token

检查 `FILL-08` 是否对聊天模板结果计数；检查 `FILL-09` 是否在每次删除后重新调用该函数。

### Q18：系统消息或最新问题被删掉

确认两者先单独保存，只从 `history` 前端成对删除。最终布尔检查必须都为 `True`。

### Q19：原始输出带 JSON 围栏

这是生成式模型的常见偏差。`FILL-10` 从第一个左花括号扫描到匹配右花括号，不应依赖固定围栏文本。

### Q20：JSON 字符串里含花括号导致过早结束

检查 `in_string` 与 `escaped` 状态；字符串内部的花括号不能改变 `depth`。

### Q21：`model_validate_json` 报字段类型错误

先查看 `raw_output`，区分模型把数字写成文字，还是 `FILL-11` 类型声明错误。不要在校验前静默强制改值。

### Q22：重复关键词没有被拒绝

检查 `FILL-12` 是否在清洗后比较列表长度与集合长度，并返回 `cleaned`。

### Q23：高难度、短时间案例仍通过

检查 `FILL-13` 是否同时使用 `difficulty >= 4` 与 `estimated_minutes < 30`，并在违反时抛出 `ValueError`。

### Q24：没有生成 `structured_result.json`

只有 `validation=PASS` 才写出文件。若失败，先保留原始错误；修正 FILL 实现后再运行本地结构化脚本。

### Q25：在线脚本返回 401

密钥可能无效、过期或缺少权限。请从授权服务重新获取，并且不要把密钥发给任何人代为排查。

### Q26：在线脚本返回 404

常见原因是 `LLM_BASE_URL` 路径或 `LLM_MODEL` 名称不正确。以服务提供者的官方控制台和文档为准。

### Q27：在线脚本返回 429

配额不足或请求过快。等待服务建议的重试时间，检查账户配额；不要循环高频请求。

### Q28：在线脚本超时

骨架超时为 60 秒并最多重试 2 次。检查网络和服务状态；可选部分失败不影响本地必做结果。

### Q29：在线脚本返回请求过大或 413

缩短消息、图像或附件；本实验只有短文本，若仍发生通常是基础地址或网关配置异常。

### Q30：接口返回文本但校验失败

网络层成功不等于应用层成功。保留 `validation=FAIL` 和错误详情，说明是哪条模式或业务规则被违反。

### Q31：如何保护 API 密钥

仅通过 `Read-Host -AsSecureString` 输入到当前会话，结束后清空变量。请勿把密钥写入源码、报告、JSON、截图或版本库。

### Q32：提示中包含“忽略规则”怎么办

外部文本可能包含提示注入。系统消息不是绝对安全边界；应用仍需最小权限、结构校验和人工审查。本实验不要把不可信文本拼入系统指令。

* **提示注入（prompt injection）**：不可信输入中夹带了试图改变模型行为的指令，例如要求忽略原有规则或泄露信息。
